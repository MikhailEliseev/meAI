## 🎯 Главная цель проекта (одной фразой)

**Клиент (владелец клиники) вбивает URL своего сайта в чат на iamaim.ru → через ~20 минут получает полный отчёт конкурентной разведки на сайте с рекомендациями.**

---

## 🎯 Что должно произойти (идеальный юзкейс)

```
1. Клиент заходит на iamaim.ru
2. Видит чат, вбивает: "https://my-clinic.ru"
3. Hermes (LLM-агент) начинает интерактивное общение:
   - Со стримингом сообщений (bubble-эффект)
   - Со статусами "сейчас делаю X" (wow-эффект)
   - Даёт комментарии на лету: "Нашёл 5 конкурентов в радиусе 2км..."
4. За ~20 минут Hermes прогоняет 14-16 фаз pipeline:
   - prescan, competitors, ci_analysis, seo/tech/content audit
   - social (instagram, reviews, smi), doctor dossiers
   - hh analysis, finance, geo audit, etc.
5. В чате появляется ссылка: "Ваш полный отчёт готов: https://iamaim.ru/reports/{hash}"
6. Клиент открывает отчёт на сайте — полная картина:
   - Конкуренты (кто они, что делают)
   - Слабые места клиента
   - Рекомендации AIM что сделать
   - Планы по всем инструментам
7. В конце отчёта — CTA: "Закажите глубокий разбор у Михаила"
```

**WOW-эффект = клиент видит, что система разобрала его бизнес за 20 минут глубже, чем он сам его знает.**

## 📅 Хронология разработки (2 месяца)

### Май 2026 — начало

**1 мая:** старт проекта. Задумывал как **мультиагентную систему с регистрацией** для решения полноценных маркетинговых задач для медицинских организаций.

**Май (первые 3-4 недели):** пробы и ошибки. Писал код "в пустую" — несвязанные куски, которые не работали вместе. ~30 дней хаоса.

### Конец мая — июнь — нащупывание

**~6 июня:** первые backup'ы. Нащупал отклик от одного инструмента — **Hermes**, чат-бота на базе Nous Research Hermes Agent.

**Открытие:** Hermes — самообучающаяся система, может:
- Контактовать через Telegram и через сайт
- Вести себя как project manager / маркетолог / чат-бот
- Главное: **первая коммуникация с клиентом + сбор информации + запуск 14-16 фазного pipeline**

### Июнь — развитие

**Попытка сделать жёсткий pipeline (версия v6 или v7):**
- Жёсткие вызовы tools по Python-коду, без LLM-оркестрации
- **Результат:** плохие отчёты, плохая интерпретация данных
- Hermes не справлялся с детерминированным потоком
- Версия с жёстким pipeline провалилась

**Открытие:** схема с LLM-оркестратором максимально жизнеспособна. Даже когда Hermes получает данные 3 раза и выдаёт отчёт — это лучше, чем жёсткий pipeline.

**Pivot от PM-функций:** изначально задумывал, что Hermes создаст базу клиентов как project manager (узнавать проекты, и прочее). **Отказался от этой идеи** — понял, что даже конкурентная разведка и поддержание диалога при текущем коде/нагрузке/инфраструктуре практически невозможны.

### 30 июня (сегодня) — точка слома

**Сейчас:** чат + дизайн + стриминг работают. Но пользователь НЕ получает финального результата.

**Что не работает:**
- Hermes теряет инструменты
- Не знает куда идти, какой инструмент вызывать
- Pipeline не завершается до конца
- Отдельные инструменты недособирают данные
- Hermes перескакивает с инструмента на инструмент, может забыть какой-то
- Итогового финального отчёта со ссылкой НЕТ

## 🧠 Анализ от Claude Code (после полного code review)

### Что мешает Hermes дойти до конца (по данным аудита)

**Проблема 1: Слишком много tools (67 шт)**
- LLM путается в ассортименте
- Соблазн вызвать не тот tool
- 9 firecrawl variants, 3 scraping approaches (crawlee/scrapy/firecrawl)
- Много дублирующих run_* tools

**Проблема 2: aim-app backend не работает**
- `InvalidPasswordError` PostgreSQL — endpoints падают
- Hermes вызывает tool → tool делает HTTP запрос к aim-app → 500 error → LLM теряет контекст
- 67 tools зависят от неработающего backend

**Проблема 3: Стриминг рвётся**
- CLAUDE.md: "стримы рвутся на ~120с"
- 14-16 фаз pipeline = ~20 минут
- Один стрим не выдержит
- SSE deadline в коде: 600s (10 минут) — может быть достаточно, но не уверен

**Проблема 4: session_archive баг**
- Все фазы логируют `[ERROR] session_archive: failed to save`
- Данные между фазами не сохраняются корректно
- Hermes может не увидеть результаты предыдущей фазы

**Проблема 5: SOUL.md даёт противоречивые инструкции**
- В образе: 47 KB, про "3-проходный цикл"
- В volume: 106 KB, про "армию AI-агентов (4 Magisters, 70+ субагентов)"
- LLM получает mixed signals

**Проблема 6: нет детерминизма для pipeline**
- run_full_scout существует, но LLM может его НЕ вызвать
- LLM предпочитает вызывать отдельные tools (run_prescan, find_competitors, etc.)
- Так как run_full_scout = самый длинный tool, LLM его "боятся"

### Что РАБОТАЕТ хорошо (основание для надежды)

1. **LLM-оркестрация — правильная архитектура** (smoke test подтверждает)
2. **Чат продукт работает** (46 запросов/24h)
3. **67 tools регистрируются** и доступны
4. **Отдельные tools работают** (find_competitors, ci_analysis, seo_audit — видны в логах)
5. **Дизайн системы готов** (design-showcase-dual-theme.html, чат bubble стриминг)
6. **WordPress + MariaDB стабильно** (90 страниц, active theme)
7. **Hermes state.db работает** (32 сессии, 161 сообщение)
8. **Key rotation работает** (14 Apify + 15 Firecrawl ключей)
9. **Telegram bot работает** (webhook + polling)

### Ключевой инсайт

**Система НЕ настолько сломана, как кажется.** Основная проблема — КУЧА ШУМА вокруг рабочего ядра:

- Рабочее ядро: Hermes + 67 tools + WordPress chat + DeepSeek
- Шум: PostgreSQL (не нужен), magisters/subagents (deprecated), backend CRM (не используется), aim-paperclip (unknown), HeadroomGuard (не активен), pipeline v7 (не используется), 152 файла zombie кода

**Если убрать шум — ядро может задышать.**

## 🎯 Моя рекомендация: Путь C (Radical Simplification)

**Не сносить всё. Не чинить существующее.** Сделать хирургическое удаление лишнего.

### Почему НЕ Путь B (снос и переезд)

- Рабочее ядро уже есть — rewrite = потерять 2 месяца
- Те же проблемы всплывут на новом сервере (если не починить архитектуру)
- Ценность — в существующих 67 tools иkey pools (14+15 ключей уже настроены)
- Переезд = 1-2 недели даунтайма

### Почему НЕ Путь A (точечные фиксы)

- Без удаления магистров/субагентов код останется запутанным
- LLM будет продолжать теряться в 67 tools
- Backend CRM (если починить PG) — лишний слой для поддержки

### Путь C — конкретный план

**Фаза 1: Стабилизация (1-2 дня)**
- Починить PostgreSQL auth (или убрать PG совсем)
- Починить session_archive баг
- Синхронизировать SOUL.md
- Закрыть exposes порты

**Фаза 2: Кардинальная чистка (2-3 дня)**
- Удалить magisters (19 файлов)
- Удалить subagents (133 файла)
- Удалить pipeline v7 (2692 строки)
- Удалить EventBus
- Удалить obsidian vaults (кроме architect)
- Удалить `.venv`, `.planning`, backups, logs

**Фаза 3: Фокус на конкурентной разведке (3-5 дней)**
- Сделать run_full_scout ЕДИНСТВЕННЫМ способом запустить pipeline
- Скрыть от LLM отдельные run_* tools (или объединить)
- Починить 14-16 фаз внутри run_full_scout
- Гарантировать что session_archive сохраняет каждую фазу
- Финальный отчёт публикуется на сайте (через publish_scout_report)

**Фаза 4: UX проверки (1-2 дня)**
- Открытый URL клиентом → трёх-сообщений формат ответа Hermes → ссылка на отчёт
- Smoke test: вбить URL → дождаться отчёта → открыть
- Проверить что ВСЕ 14 фаз завершаются

**Итого:** 7-12 рабочих дней до работающего продукта.
