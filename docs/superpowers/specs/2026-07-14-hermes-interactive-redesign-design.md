## 1. Контекст — что не так сейчас

Гермес (контейнер `aim-hermes`) работает по **жёсткому 13-фазному pipeline**:
движок `engine.py` (2059 строк) прогоняет все 13 фаз последовательно через
обычный `for phase in PHASES:` (`engine.py:176`). Нет ветвлений, нет пауз,
нет диалога с клиентом. Полностью автономный прогон ~17 минут → один большой
HTML-отчёт.

**Проблема, которую решаем:** длинный негибкий отчёт, в котором модель
ошибается из-за объёма. Хотим «база → диалог → по запросу»: быстрый первый
ответ (~3 мин) с основными маркетинговыми показателями, затем Гермес
предлагает релевантные действия кнопками и запускает инструменты только по
запросу клиента.

```
  │                                          │
  │ 🎯 Топ-3 конкурента:                     │
  │    1. Конкурент А — рейтинг 4.7, 52 отз  │
  │    2. Конкурент Б — рейтинг 4.5, 88 отз  │
  │    3. Конкурент В — рейтинг 4.8, 31 отз  │
  │                                          │
  │ Можно копнуть глубже:                    │
  │ [Глубокий анализ конкурентов]            │
  │ [Проверить соцсети]                      │
  │ [Упоминания в СМИ]                       │
  │ [Анализ отзывов]                         │
  │                                          │
  │ Или спросите своим словами 👇            │
  └─────────────────────────────────────────┘

КЛИЕНТ: [жмёт «Упоминания в СМИ»]
  → Гермес вызывает run_smi_mentions → ~1-2 мин → показывает выжимку
  → снова предлагает кнопки (адаптивно: что ещё не смотрели)

КЛИЕНТ: «а сколько они тратят на рекламу?»
  → Гермес сам выбирает тул (run_ads_intelligence) → отвечает

[Когда клиент насытился:]
ГЕРМЕС: «Собрать всё в отчёт?» → [Собрать отчёт] → generate_html_report
  → + в конце базы/отчёта: питч услуг AIM
```

**Принципы диалога (умные подсказки + текст):**
1. После базы Гермес **анализирует результат** и предлагает релевантные кнопки
   (плохой сайт → подсветит «тех.аудит»; много плохих отзывов → «анализ отзывов»).
2. Кнопки — не единственный путь; клиент всегда может писать свободным текстом.
3. Гермес ведёт диалог инициативно, но не навязчиво (максимум 4 кнопки за раз).
4. В конце первой фазы базы — **питч услуг AIM** («поможем с ...»).

## 4. Архитектура — новый контейнер `aim-hermes-v2`

### 4.1 Разделение ответственности

```
aim-hermes-v2 (НОВЫЙ, тонкий «мозг» ~300 строк):
  - FastAPI /api/chat/stream (SSE, совместимый с Theme-чатом)
  - Диалоговый промпт (системный промпт Гермеса v2)
  - Tool-definitions (OpenAI function-calling schema, ~10 тулзов)
  - Thin-wrappers: HTTP-клиенты к aim-app:8000
  - Session storage (SQLite + session_archive/)

aim-app:8000 (БЕЗ ИЗМЕНЕНИЙ — endpoint'ы для 3 прокси-тулов):
  - /api/competitors/find, /api/competitors/analyze, /api/seo/audit, ...
  (тяжёлая логика конкурентов/SEO остаётся здесь)
```

### ⚠ ВАЖНО: тулзы НЕ все тонкие прокси (исправлено 2026-07-14)

Проверка кода показала, что из 10 тулов **только 3 — настоящие HTTP-прокси**
к `aim-app:8000`. Остальные **7 — толстые самостоятельные модули**, которые
сами дёргают внешние API (Perplexity, Apify, Firecrawl, Playwright) и сами
пишут в WordPress-базу. Они живут *внутри* контейнера `aim-hermes`.

| Тул | Тип | Куда реально ходит |
|---|---|---|
| `find_competitors` | ✅ прокси | aim-app (5 ссылок на AIM_API_BASE) |
| `run_ci_analysis` | ✅ прокси | aim-app (3) |
| `run_seo_audit` | ✅ прокси | aim-app (5) |
| `run_smi_mentions` | ❌ толстый | Perplexity напрямую (0 ссылок на aim-app) |
| `run_review_platforms` | ❌ толстый | Perplexity напрямую |
| `run_instagram_content` | ❌ толстый | Apify напрямую |
| `run_pagespeed` | ❌ толстый | Playwright (локальный Chromium) |
| `run_ads_intelligence` | ❌ толстый | Firecrawl напрямую |
| `generate_html_report` | ❌ толстый | WordPress DB (pymysql) напрямую |
| `perplexity_search` | ❌ толстый | Perplexity API напрямую |

**Следствие:** контейнер v2 будет НЕ лёгким (~300 строк), а должен
содержать 7 перенесённых толстых тулов + их внешние клиенты. Это
осознанный выбор подхода A — пользователь явно предпочёл основательность
скорости. Объём работ больше, но результат — чистый автономный контейнер.

**Стратегия переноса:** копируем 7 толстых модулей из
`hermes-container-code/app/tools/` (бэкап) в `hermes-v2/app/tools/` как есть,
адаптируя только импорты (`from app.tools.X` → наши пути) и регистрацию
в OpenAI tool-calling схеме. Ключи (Perplexity, Apify, Firecrawl) — те же
env-переменные, что у старого hermes (`PERPLEXITY_API_KEY`,
`APIFY_API_TOKEN`, `FIRECRAWL_API_KEY`).

## 5. Системный промпт (диалоговая политика)

Системный промпт задаёт Гермесу «характер» и правила. Структура:

```
Ты — Гермес, AI-ассистент маркетингового агентства AIM. Помогаешь
клиникам и медицинским центрам разобраться в своём рыночном положении.

## Твои принципы
1. Сначала база. Когда клиент присылает сайт — вызови quick_overview
   и find_competitors (ОДИН раз каждый). Это твоя первая реакция.
2. База должна быть быстрой и информативной. Покажи: чем занимается
   клиника, город, специализация, ключевые цифры рынка, top-3 конкурента.
3. После базы — НЕ запускай ничего автоматически. Проанализируй результат
   и предложи 2-4 релевантные кнопки («что ещё посмотреть»).
4. Запускай дополнительные инструменты ТОЛЬКО когда клиент:
   - нажал кнопку, ИЛИ
   - явно попросил (текстом, например «проверь соцсети»).
5. Веди живой диалог. Отвечай на вопросы клиента своими словами.
6. Когда клиент насытился — предложи собрать отчёт (generate_html_report).
7. В конце базовой разведки коротко расскажи, чем может помочь AIM
   (SEO, контекстная реклама, SMM, репутация). Не навязчиво.

## Как предлагаешь кнопки
- После каждого ответа с данными, показывай 2-4 кнопки с действиями,
  которые имеет смысл сделать дальше (исходя из того, что уже посмотрели).
- Формат кнопок в ответе: специальная JSON-разметка (см. протокол кнопок).
- Адаптируй кнопки: если у клиники плохой сайт — предложи «тех.аудит»;
  если много плохих отзывов — «анализ отзывов»; если активный Instagram —
  «анализ соцсетей».

## Тон
Профессиональный, дружелюбный, по делу. На русском. Цифры конкретные.
Не увертюры из 5 абзацев — сразу к сути.

## Границы
- Не вызывай find_competitors больше одного раза за сессию.
- Не вызывай несколько «тяжёлых» тулов (ci_analysis, ads) одновременно.
- Если данных нет — скажи честно «по этому источнику данных не нашлось».
```

## 6. Протокол кнопок в чате

Backend (v2) и фронтенд (Theme-чат) договариваются о формате. Расширяем
существующий SSE-протокол аддитивно (старые клиенты игнорят новые события).

### 6.1 Новое SSE-событие `suggestions`

```json
{
  "type": "suggestions",
  "buttons": [
    {"label": "Глубокий анализ конкурентов", "tool": "run_ci_analysis"},
    {"label": "Проверить соцсети", "tool": "run_instagram_content"},
    {"label": "Упоминания в СМИ", "tool": "run_smi_mentions"},

```

Backend эмитит это событие после текстового ответа, когда есть что
предложить. Фронтенд рендерит кнопки под сообщением ассистента.

### 6.2 Изменения в Theme-чате

| Файл | Изменение |
|---|---|
| `useStreamChat.js:250` | добавить `case 'suggestions'` → `setActiveButtons(event.buttons)` |

Не нужен structured payload. Это минимизирует изменения на фронтенде.

## 7. Управление сессиями и состоянием

### 7.1 Сессия

- `session_id` — client-supplied (как сейчас). Хранится в SQLite.
- История диалога — список сообщений `[user, assistant, tool_call, tool_result, ...]`.
- На каждый ход модели подаём: системный промпт + история + новые tool-results.
- Контекстное окно: при росте истории (>20 сообщений) суммаризуем старые
  tool_results в компактное «что уже узнали» (отдельный LLM-вызов, cheap).

### 7.2 Данные между тулзами

Сейчас `engine.py` аккумулирует: Perplexity → ИНН/город → финансы. Без
движка модель прокидывает данные через историю диалога: результат каждого
тула возвращается структурированно (JSON), и модель в следующих вызовах
видит его. Для надёжности thin-wrappers возвращают «переиспользуемый»
вывод (с ИНН, городом, URL) — чтобы последующий тул мог их взять из
истории, а не переспрашивать у модели.

### 7.3 Архив сессий и отчёты

- Каждый tool-result пишется в `/opt/data/sessions-archive/{hash}/`.
- `generate_html_report` читает весь архив сессии (как сейчас делает
  `generate_html_report.py` через `session_archive.load_all_data`).
- Отдельный volume `/opt/hermes-v2-data` (не мешаем со старым).

## 8. Маршрут деплоя

1. Разработка локально в `~/Desktop/Dev/meAI_1/AIM/hermes-v2/`.
2. `rsync` на сервер в `/opt/aim/AIM/hermes-v2/`.
3. `docker compose build hermes-v2 && docker compose up -d hermes-v2`.
4. Тест на изолированном endpoint (сначала без переключения nginx).
5. Когда работает — переключаем nginx `aim-hermes:8000` → `aim-hermes-v2:8000`.
6. Старый `aim-hermes` НЕ удаляем — выключен, для отката.

**Безопасность:** до шага 5 клиенты не видят v2. Полная возможность отката
до момента переключения nginx.

## 9. Тестирование

- **Unit-уровень:** thin-wrappers мокаются (проверка schema тулзов).
- **Интеграционный:** тестовый URL через v2, проверка что тулзы зовут
  aim-app корректно.
- **Сценарии:** (а) URL → база → кнопки; (б) URL → база → кнопка → ответ;
  (в) URL → база → свободный текст → тул; (г) сборка отчёта.
- **Регресс:** сравнить базовый ответ v2 vs старый pipeline по времени
  (цель: база за ≤4 мин vs 17 мин сейчас).

## 10. Риски и митигации

| Риск | Митигация |
|---|---|
| Модель вызывает тулы хаотично / лишний раз | Жёсткие описания «когда вызывать» + ограничения в промпте («один раз за сессию») |
| Потеря данных между тулами (без движка) | Thin-wrappers возвращают структурированный JSON с ИНН/городом/URL; модель видит в истории |
| Контекст забивается tool-results | Суммаризация истории при >20 сообщений |
| Новый контейнер «не заводится» | Тестируем изолированно до переключения nginx; старый aim-hermes — откат |
| Доступ к WP DB для отчётов | Те же env, что у старого hermes (`WP_DB_*`) |
| Длительность базы >4 мин | `find_competitors` без `run_ci_analysis` (CI уходит в кнопку); мониторим |

## 11. Что НЕ входит в скоуп v2

- Next.js-чат (`/chat-test`, `/chat-new`) — не трогаем, он тестовый.
- Telegram-бот — оставляем как есть (работает на старом aim-hermes),
  миграция на v2 — отдельная задача после подтверждения, что чат работает.
- Удаление старого `aim-hermes` — только после недели стабильной работы v2.
- Скиллы (`./hermes/skills/`) — не переносим в v2 на первом этапе.

## 12. Критерии успеха

1. Клиент шлёт URL → за ≤4 мин получает базу (рынок + top-3 конкурента) с кнопками.
2. Кнопки в чате работают → запускают соответствующий инструмент.
3. Свободный текст клиента корректно триггерит тулзы.
4. Гермес предлагает сборку отчёта → отчёт генерируется из данных сессии.
5. В базовом ответе — питч услуг AIM.
6. Старый контейнер `aim-hermes` доступен для отката в любой момент.
