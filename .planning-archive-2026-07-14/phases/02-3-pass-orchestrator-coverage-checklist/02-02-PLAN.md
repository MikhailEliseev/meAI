<objective>
Построить LLM-оркестратор с 3-проходным циклом (Collect → Gap-analyze → Fill+Assemble) в новом модуле app/orchestrator/. Это архитектурное ядро Phase 2 — воспроизводит успешный паттерн v1 (LLM свободно выбирает инструменты) + добавляет структурированный 3-pass цикл с авторежимом.

Purpose: LLM уже имеет доступ к 49 инструментам через registry, но текущий PRESALE режим — это один неструктурированный AIAgent.run_conversation() вызов. Без явных pass-границ LLM часто «забывает» позвать критичные инструменты (Instagram, find_doctor_handles) и не имеет понятия «гэп-анализ». 3-pass структура заставляет LLM дважды рефлексировать: что собрано и чего не хватает — перед тем как генерировать HTML.

Output: 6 новых файлов в app/orchestrator/, 1 изменённый agent_wrapper.py. Оркестратор OPT-IN через env var (ORCHESTRATOR_MODE=1). PipelineEngine остаётся нетронутым как fallback (ORC-05).

Архитектурное решение (locked, PROJECT.md Key Decisions + RESEARCH.md Section 5.2): Option 2 — orchestrator-first, bypass _TOOL_HANDLERS для tool dispatch.
</objective>

<design_decisions>
**Решение 1: 3 отдельных AIAgent.run_conversation() вызова, не один мега-промпт.**
Почему: success criteria #1 требует "3 distinct passes executing automatically". Если всё в один call — это один pass, не три. Раздельные calls дают явные pass-границы для логирования и QC gate.

**Решение 2: ORCHESTRATOR_MODE env var = OPT-IN, по умолчанию OFF.**
Почему: aim-hermes контейнер LIVE в production. Менять PRESALE routing по умолчанию = рисковать даунтаймом. Env var даёт safe rollout: тестирование локально → деплой с ORCHESTRATOR_MODE=0 → переключение на =1 когда подтверждено stable.

**Решение 3: Pass 2 в 02-02 использует MINIMAL checklist (5 пунктов).**
Почему: полный 15-item checklist — content Plan-а 02-03. В 02-02 мы строим plumbing: Pass 2 существует, вызывается, возвращает gap_report. Минимальный чек-лист: competitors collected? clinic_url parsed? doctors found? instagram called? html generated? В 02-03 этот список заменится на полный.

**Решение 4: Оркестратор НЕ пишет свой tool dispatch layer.**
Почему: AIAgent.run_conversation() УЖЕ умеет вызывать tools через registry. Оркестратор = structured prompts + state tracking. Никаких `import tools.registry` в orchestrator/ — только AIAgent calls.

**Решение 5: OrchestratorState — простой dataclass, не SQLite.**
Почему: pipeline уже персистит в PipelineState (state.db через SessionDB). OrchestratorState in-memory для одного run; long-term persistence — через SessionDB conversation history. Если run упал — restart с нуля, как и PipelineEngine сейчас.

**Решение 6: Если оркестратор падает с exception — fallback на PipelineEngine.execute().**
Почему: ORC-05 требует pipeline остаётся как alternative. Fallback = graceful degradation. Если 3-pass logic ломается, клиент всё равно получает отчёт (пусть и pipeline-quality).
</design_decisions>
