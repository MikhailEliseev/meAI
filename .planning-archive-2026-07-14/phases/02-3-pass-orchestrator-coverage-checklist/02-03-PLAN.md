<objective>
Реализовать 15-item QC checklist (RESEARCH.md Section 5.4), gap-analysis logic, coverage % reporting, и HTML BUILD gate. Это второй architectural pillar Phase 2 — превращает «3-pass cycle» из инфраструктуры в измеримую систему качества.

Purpose: 02-02 построил orchestrator plumbing, но Pass 2 использует minimal 5-item checklist. Без полного 15-item checklist (QC-01), без QC gate перед HTML (QC-02), без coverage report (QC-03), и без 80% target (QC-04) — оркестратор не имеет объективной метрики полноты. LLM по-прежнему может «забыть» Instagram для косметологии, не найти конкурентов, не получить динамику выручки. Этот plan даёт оркестратору teeth: explicit checklist + gate + honest report.

Honest-data principle (ORC-04): если пункт checklist не заполнен — он marked "данные недоступны" с reason, НЕ выдумывается. Это явный контраст с поведением v4 где LLM порой фальсифицировал данные чтобы «закрыть» секцию.

<design_decisions>
**Решение 1: QC_CHECKLIST — Python module-level constant, не dataclass.**
Почему: checklist статичный (15 пунктов с pass criteria). Module-level list of dicts позволяет iterate, filter, и version. Если понадобится версионирование — добавить VERSION field.

**Решение 2: LLM сам оценивает заполненность пункта (не Python-парсер).**
Почему: Python не может определить «≥3 doctors with ФИО (not clinic name)» без сложного regex. LLM видит collected_data и принимает solution — это его сильная сторона. Парсер только суммирует ответы LLM.

**Решение 3: Pass 2 prompt = QC_CHECKLIST render + JSON output contract.**
Почему: каждый пункт checklist имеет clear pass criterion. LLM оценивает каждый пункт: filled / partial / missing + reason. Парсим JSON, считаем coverage %.

**Решение 4: QC gate — soft, не hard.**
Почему: hard gate (блокировать HTML при < 80%) рискованный — клиент может остаться без отчёта вообще. Soft gate: Pass 3 видит gap_report и старается заполнить, но если не получается — HTML всё равно генерируется с пометкой «данные недоступны». Это соответствует ORC-04.

**Решение 5: Coverage report в HTML — отдельная секция «QC Coverage».**
Почему: transparency для клиента и для админа. Видно что собрано, что НЕ собрано и почему. Это само по себе honesty signal — «мы не скрываем что не нашли».

**Решение 6: Coverage metadata — optional parameter в handle_generate_html_report.**
Почему: generate_html_report вызывается и из PipelineEngine (ORC-05 fallback), не только из orchestrator. PipelineEngine сейчас не передаёт coverage metadata. Optional → обратная совместимость сохраняется.
</design_decisions>
