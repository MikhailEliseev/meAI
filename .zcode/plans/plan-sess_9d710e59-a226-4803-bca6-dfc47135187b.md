# План: Golden-тесты качества ответов чата AIM

## Цель
Создать измеримый базис «качества ответа» (а не «работает/упало»), чтобы:
1. Зафиксировать текущее состояние **до починки** (базлайн — ожидаемо плохой).
2. После каждого фикса P0 перезапускать и видеть, как растут метрики.

Тесты directly валидируют диагноз: главный чек (G1 Grounding) измеряет ровно P0-1 — «опирается ли LLM на данные».

---

## Подход
- **Точка входа:** `app.llm.chat_with_tools(history)` (`llm.py:729`) — async-генератор событий. Вызываем напрямую, **без HTTP/SSE**, собираем весь вывод.
- **Исполнение:** внутри контейнера `aim-hermes-v2` на сервере (`docker exec`) — production-faithful, все ключи уже в env.
- **Паттерн snapshot (run-once / assert-many):**
  - `--refresh` → прогон через РЕАЛЬНЫЕ API (Perplexity/Apify/FNS/LLM), запись snapshot. Медленно + токены.
  - без флага → проверки на существующем snapshot. Быстро + бесплатно (для частых прогонов).
- **Клиники:** я сам найду 5 реальных РФ-клиник разного профиля (крупная сеть / середняк / спартанский сайт) через web-search.

---

## Что проверяем (чеки — ядро «релевантности»)

| ID | Чек | Что ловит | Связь с дефектом |
|----|-----|-----------|------------------|
| **G1** | **Grounding** — каждая цифра/имя/рейтинг в тексте LLM должна встречаться в `formatted_blocks` | LLM выдумывает цифры, которых нет в данных | **P0-1** (LLM не видит данные) — главный сигнал |
| **G2** | **Structure** — секции Позиция/Сильные/Рост/Отзывы/Рекомендации присутствуют | LLM не следует спецификации промпта | поведение LLM |
| **G3** | **Clean output** — нет сырого JSON, `4.300000190734863`, `:::`, утечки `[SUGGESTIONS]`, «трафик/визиты», Instagram/TG-рек | симптомы из истории коммитов + 148-ФЗ | **P1** (R1, R2), compliance |
| **G4** | **Data completeness** — каждый тул вернул непустые/не-error данные | каскад мусора из Perplexity/FNS | **P1** (T2) |
| **G5** | **Coherence** — текст не противоречит сам себе (лидер vs отстаёт) | спутанность от противоречивых промптов | **P0-2** |
| **JUDGE** | LLM-as-judge (опционально) — рубрика 0-5: релевантность/польза/grounding/продажность | единый трекаемый скор | сводный |

Scorecard показывает **примеры** неграундированных цифр («ungrounded: 380 млн, 4.8★»), чтобы диагноз был наглядным.

## Выход первой итерации (базлайн «до»)
Терминальный scorecard, например:
```
CASE            G1 ground  G2 struct  G3 clean  G4 data  JUDGE
stom-krd-01      12% ❌     5/5 ✅    FAIL ❌   3/4 ⚠    2.1/5
dent-msk-02       8% ❌     4/5 ⚠    FAIL ❌   2/4 ❌    1.8/5
...
BASELINE AVG     10%        90%       0% pass   60%      1.9/5
```
Ожидание: G1 ~10% (LLM не видит данные → почти все цифры ungrounded), G3 FAIL (сырой JSON/float утекают). **Это и есть доказательство диагноза числами.** После фикса P0-1 G1 должен прыгнуть к 70-90%.

## Допущения / риски
- `app.llm.chat_with_tools` импортируется в контейнере с ключами в env — проверю на шаге 1, адаптирую bootstrap если надо.
- `--refresh` зовёт платные API → по умолчанию НЕ автообновляется, только по явному флагу.
- Публикация отчёта в WP при refresh → добавлю env-флаг `GOLDEN_SKIP_PUBLISH=1` (минимальная правка-гвард в `llm.py`, обёрнута так, что вне golden-режима поведение не меняется).

## Шаги реализации
1. На сервере: верифицировать импорт `app.llm` в контейнере + наличие ключей в env. Найти, примонтирован ли код (иначе `docker cp`).
2. Web-search: подобрать 5 реальных клиник, записать в `cases.yaml`.
3. Написать `run_golden.py` (capture событий chat_with_tools → snapshot.json + transcript.md).
4. Написать `checks.py` (G1-G5), `judge.py` (опц.).
5. Прогнать `--refresh` на сервере → получить базлайн-scorecard.
6. Показать scorecard + вывод конкретных ungrounded-цифр как численное доказательство диагноза.
