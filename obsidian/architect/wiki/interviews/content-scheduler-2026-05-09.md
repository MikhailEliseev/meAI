# Интервью: Content Scheduler Agent

**Дата:** 2026-05-09 22:00 GMT+3

## Блок 1: Роль и уникальность

**Q1: Что делает Content Scheduler Agent?**

A: Автономный контент-менеджер, который получает готовый контент от других агентов, формирует контент-план, получает утверждение от пользователя и публикует контент по расписанию во все каналы.

**Уточнение:** Это не просто планировщик, а полноценный контент-менеджер с логикой принятия решений.

**Q2: Кто родительский Magister?**

A: Social Magister

**Q3: Почему это критично для агентства?**

A: Без Content Scheduler контент создаётся, но не публикуется → нет результата, нет статистики, нет трафика. Это критичная точка отказа.

**Уникальная ценность:**
- **Централизованное управление публикациями** — один контент-план для всех каналов
- **Автоматизация публикаций** — контент публикуется по расписанию без ручной работы
- **Контроль и прозрачность** — пользователь видит весь контент-план и статусы публикаций
- **Гибкость** — можно изменить контент-план после утверждения

## Блок 2: Входные данные

**Q4: Откуда берутся данные?**

A: Готовый контент от других агентов:
- Content Magister (статьи, тексты)
- Trend Watcher Agent (сценарии, ролики)
- Blog Content Agent (статьи для блога)
- Landing Content Agent (тексты для лендингов)
- AI Sales Admin Agent (посты для соцсетей)

**Q5: Какие обязательные параметры?**

A:
- `content: dict` — готовый контент (текст, изображения, видео)
- `channels: list[str]` — каналы для публикации (Instagram, YouTube, Telegram, VK, Dzen, WordPress, Bitrix24)
- `schedule: dict` — расписание публикаций (дата, время, канал)

**Опциональные:**
- `approval_required: bool` — требуется ли утверждение (по умолчанию True)
- `retry_count: int` — количество попыток при ошибке (по умолчанию 10)
- `notification_time: str` — время ежедневных уведомлений (по умолчанию "20:00 GMT+3")

## Блок 3: Алгоритм работы

**Q6: Какие основные шаги?**

A: 7 шагов:
1. Получение готового контента от агентов (через Event Bus)
2. Формирование контент-плана (календарь в Airtable/Notion/Google Sheets)
3. Отправка контент-плана на утверждение пользователю (через Operator)
4. Публикация контента по расписанию после утверждения
5. Мониторинг статусов публикаций (опубликовано/ошибка/отложено/в очереди)
6. Обработка ошибок и retry (10 попыток, 5 минут интервал)
7. Ежедневные уведомления (раз в день вечером через Telegram бот)

**Q7: Какие внешние API используются?**

A:
- **Instagram API** — публикация постов и сторис
- **YouTube API** — публикация видео и Shorts
- **Telegram Bot API** — публикация в канал
- **VK API** — публикация постов
- **Яндекс.Дзен API** — публикация статей
- **WordPress REST API** — публикация на блог
- **Bitrix24 API** — публикация на сайт
- **Airtable/Notion/Google Sheets API** — контент-план
- **Post My Post / Buffer API** — fallback сервисы

**Q8: Есть ли специфичная логика?**

A: Да, несколько важных моментов:

1. **Утверждение контент-плана обязательно:**
   - `approval_required: true`
   - Пользователь утверждает через Operator
   - Без утверждения контент не публикуется

2. **Оптимальное время публикации:**
   - Утро: 08:00-09:00
   - Вечер: 18:00-20:00
   - Агент предлагает оптимальное время, но пользователь может изменить

3. **Retry 10 раз при ошибке API:**
   - Exponential backoff (5 минут интервал)
   - После 10 попыток → fallback (Post My Post, Buffer)

4. **Ежедневные уведомления:**
   - Раз в день вечером (20:00 GMT+3)
   - Через Telegram бот
   - Статус всех публикаций за день

5. **Гибкость:**
   - Можно изменить контент-план после утверждения
   - Можно добавить/удалить/перенести публикации

## Блок 4: Результаты и метрики

**Q9: Что возвращает агент?**

A:
- Контент-план (URL в Airtable/Notion/Google Sheets)
- Статусы всех публикаций (pending_approval, approved, published, failed, cancelled)
- Отчёт по публикациям (сколько опубликовано, какие ошибки)
- Уведомления пользователю (через Telegram бот, раз в день вечером)

**Q10: Какие метрики качества?**

A:
- **Success rate:** > 95%
- **Execution time:** < 5 секунд на 1 публикацию
- **Процент успешных публикаций:** > 95% (из запланированных)
- **Соблюдение расписания:** публикация в точное время ±5 минут
- **Скорость реакции на ошибки:** retry в течение 5 минут

## Блок 5: Особенности и edge cases

**Q11: Какие специфичные ошибки?**

A:
1. **API_UNAVAILABLE** — API платформы недоступен (Instagram down, YouTube down) → retry 10 раз → fallback (Post My Post, Buffer) → уведомить пользователя
2. **CONTENT_MODERATION_FAILED** — контент не прошёл модерацию платформы → немедленное уведомление пользователя (критичная ошибка) → не retry (модерация не пройдёт повторно)
3. **DUPLICATE_PUBLICATION** — тот же контент уже был опубликован → пропустить публикацию → уведомить пользователя
4. **CONTENT_PLAN_NOT_APPROVED** — контент-план не утверждён пользователем → не публиковать контент → напомнить пользователю через 24 часа
5. **SCHEDULED_TIME_PASSED** — запланированное время публикации уже прошло → опубликовать немедленно (если < 1 часа прошло) → пропустить публикацию (если > 1 часа прошло)

**Q12: Что в backlog?**

A:
- Автоматическая оптимизация времени публикации (на основе статистики)
- A/B тестирование контента (разные варианты постов)
- Интеграция с аналитикой (автоматический сбор метрик после публикации)

## Комментарии и инсайты

**Во время интервью:**

**Важное уточнение:** Контент-план — это ключевой элемент взаимодействия с пользователем. Пользователь должен видеть весь контент-план и утверждать его перед публикацией.

**Вопрос:** "А, все окей, да, правильно понял. Это контент-менеджер, который получает готовый контент от других агентов и публикует его по расписанию?"

**Ответ:** Да, именно так. Но с важным дополнением — он формирует контент-план и получает утверждение от пользователя перед публикацией.

**Решения:**
- Использовать Airtable/Notion/Google Sheets для контент-плана (выбор пользователя)
- Ежедневные уведомления через Telegram бот (20:00 GMT+3)
- Fallback сервисы (Post My Post, Buffer) при недоступности API
- Гибкость системы — можно изменить контент-план после утверждения

**Инсайты:**
- Контент-план — это не просто список публикаций, а инструмент контроля и прозрачности
- Утверждение контент-плана обязательно (approval_required: true)
- Ежедневные уведомления — важный элемент взаимодействия с пользователем
- Fallback сервисы — критичны при недоступности API
