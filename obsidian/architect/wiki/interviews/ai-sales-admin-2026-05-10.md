## Финальное определение

**AI Sales Admin Agent = Виртуальный администратор клиники 24/7**

- Мониторит все каналы коммуникации (Telegram, Instagram, VK, WhatsApp, сайт)
- Отвечает по протоколам (настраиваются при setup)
- Использует структурированную базу знаний (Obsidian Vault)
- Работает круглосуточно без выходных
- Квалифицирует лидов и передаёт менеджеру
- Соблюдает 152-ФЗ (медицинские данные)

## Блок 1: Роль и уникальность

**Q1: Что делает AI Sales Admin Agent?**

A: Представитель клиники в соцсетях, который быстро и оперативно реагирует на сообщения пользователей. Это чат-бот, который может ответить на вопросы, зацепить пользователя и записать на консультацию.

**Уточнение:** Не только соцсети, а ещё другие каналы. То есть, грубо говоря, это может быть бот на базе OpenClaw, который в Телеграме может ответить. Или ещё где-либо, который обладает широкой базой знаний по продуктам. Если у него нет ответа на вопрос, то он сможет сходить поизучать исследования. То есть делать такого более-менее широкого профиля.

**Комментарий:** Давай подумаем о возможностях подключения. Дадим максимальное количество источников. Классно было бы, если бы у него была суперэкспертиза по всем продуктам, по всем ценам, по всему-всему.

**Q2: Кто родительский Magister?**

A: Social Magister

**Q3: Почему это критично для агентства?**

A: Скорость ответа = конверсия. Если ответить через 30 секунд вместо 5 минут → клиент не уйдёт к конкуренту. Омниканальность важна, потому что клиенты пишут откуда угодно (Telegram, Instagram, VK, сайт). Суперэкспертиза по всем продуктам/ценам = клиент получает точный ответ сразу, без "сейчас уточню".

**Уникальная ценность:**
- **24/7 доступность** — клиенты пишут в любое время
- **Мгновенный ответ** — < 30 секунд (конкуренты отвечают часами)
- **Омниканальность** — один агент на все каналы
- **Суперэкспертиза** — знает всё о продуктах/ценах/врачах
- **Квалификация лидов** — превращает холодных в квали-лидов
- **152-ФЗ compliance** — соблюдает закон о персональных данных

**Комментарий:** Я думаю, базу знаний надо сделать в Obsidian Vault для каждой такой истории. То есть, общую базу знаний, которая будет обходиться. И мониторить, например, сайт — это очень важно. Если там меняется цена, то база знаний была бы обновляемой.

**Источники данных:**

4. **Календарь** — расписание врачей, свободные слоты для записи
5. **Медицинские источники** — для сложных вопросов (Perplexity, PubMed)

A:

**Комментарий:** Разумеется, это подключение. Я думаю, что эта штука должна жить на сервере 100%, как и вообще все наши инструменты, чтобы они были доступны 24 на 7. Да, нужно базово знать URL проекта, где он работает, разворачивать, кстати, каждого. Чтобы не путать, надо будет, чтобы системы разворачивали каждого такого агента под конкретный проект. Чтобы не пересекались базы знаний. И да, нужно подключение по API. Скорее всего, возможно, если человек захочет голосом общаться, то нужны Assembly AI плюс какая-то минимальная модель от OpenAI, я думаю, которая сможет ответить либо с фоллбэком на бесплатной модели китайские.

## Блок 3: Алгоритм работы

**Q6: Какие основные шаги работы агента?**

A:

**Комментарий:** Здесь нужно заложить прям предпродажный какой-то механизм, посмотреть лучшие практики того, как закрывать первичку на агентском уровне. Так, чтобы быстро из холодного лида это превратилось с помощью данного инструмента, данного агента в квали-лид, но сделать это очень деликатно.

**Комментарий:** Добавить, конечно же, CRM, чтобы агент мог напрямую в CRM передавать данные даже по незначительным коммуникациям.

**Алгоритм (8 шагов):**

1. **Получение сообщения** (Telegram/Instagram/VK/WhatsApp/сайт)
2. **Создание/обновление лида в CRM** — сразу, даже если это первое сообщение
3. **Быстрый ответ** (< 30 секунд) — приветствие, подтверждение получения
4. **Квалификация лида** (предпродажный механизм):
   - Выяснить потребность (что беспокоит?)
   - Определить срочность (когда нужна консультация?)
   - Оценить готовность (готов записаться?)
5. **Ответ на вопросы** (цены, услуги, врачи) — из базы знаний Obsidian
6. **Запись на консультацию** (если квали-лид) — интеграция с календарём + обновление CRM
7. **Эскалация менеджеру** (если сложный вопрос или горячий лид) — уведомление в CRM
8. **Сохранение истории** — CRM (основное) + Obsidian (резервное + аналитика)

**Q7: Какие внешние API используются?**

A:

**Комментарий:** Ну, нужно Assembly AI для распознавания голосовых сообщений. OpenAI API для ответов, например, GPT-4o или GPT-4o-mini, очень хорошо отвечают и делают это быстро. Не знаю, какие еще с Obsidian нужны подключения, чтобы с базы данных все доставать.

**Комментарий:** Смотри, мониторинг через Playwright не даёт прям чёткой информации. Возможно, стоит подумать и добавить какой-нибудь скрипт, который чисто по коду или API будет вытаскивать информацию. Например, если это WordPress или Bitrix, то можно получить чистый прайс по элементам и следить за изменениями. Потому что могут поменять цены, а агент будет не знать.

**Внешние API:**

**Каналы коммуникации:**
- **Telegram Bot API** — получение/отправка сообщений в Telegram
- **Instagram Graph API** — Direct сообщения в Instagram
- **VK API** — сообщения в VK
- **WhatsApp Business API** — сообщения в WhatsApp
- **Website Chat API** — онлайн-чат на сайте (Jivo, Carrot quest)

**AI и обработка:**
- **Assembly AI** — транскрибация голосовых сообщений (если voice_enabled: true)
- **OpenAI API** — генерация ответов (GPT-4o или GPT-4o-mini)
- **Fallback:** DeepSeek / Qwen (китайские бесплатные модели)

**Интеграции:**
- **CRM API** — Bitrix24 / amoCRM (создание/обновление лидов)
- **Календарь API** — Google Calendar / Яндекс.Календарь (запись на консультацию)
- **Obsidian Vault** — локальное чтение базы знаний (файловая система)

**Мониторинг сайта (обновление базы знаний):**
- **WordPress REST API** — получение страниц, услуг, цен (`/wp-json/wp/v2/`)
- **Bitrix24 REST API** — получение каталога товаров/услуг
- **Schema.org парсинг** — структурированные данные (если есть)
- **Playwright** — fallback (если нет API)
- **Perplexity API** — поиск медицинских исследований (для сложных вопросов)

**Q8: Есть ли специфичная логика?**

A:

**Комментарий:** Слушай, это надо будет выяснять на процессе обучения и сетапа агента. Когда мы будем сетапить агента, то надо будет в зависимости от проекта и клиента брать с него требования и обсуждать этот вопрос. То есть, грубо говоря, первоначальные инструкции мы будем закладывать на этапе сетапа.

**Комментарий (КРИТИЧНО):** Ещё важное уточнение: сейчас, наверное, стоит подумать про медицинские данные. То есть, грубо говоря, если пациент пишет и говорит о том, что 'я уже у вас был, узнайте меня, пожалуйста', тут точно этап, когда надо включаться менеджеру, потому что медицинские данные через API нельзя передавать. Это попадает под закон 152-ФЗ. То есть, как только пациент просит: 'А посмотрите, я здесь был', обращение идет к базе, и нужно заворачивать и переключать на менеджера.

**Специфичная логика:**

**Основная логика:**
1. **Скорость ответа < 30 секунд** — критично для конверсии
2. **Деликатный ToV** — медицинская специфика, без давления
3. **Квалификация через вопросы** — настраивается при setup под каждый проект
4. **Автоматическая запись в CRM** — все коммуникации, даже незначительные

**КРИТИЧНО: 152-ФЗ (Медицинские данные):**
- Если пациент просит посмотреть историю болезни / предыдущие визиты → **немедленная эскалация менеджеру**
- Агент НЕ имеет доступа к медицинским данным (закон 152-ФЗ)
- Ключевые фразы: "я уже у вас был", "посмотрите мою историю", "мои анализы", "что мне назначали", "мои результаты", "моя карта", "мои записи"
- Сообщение пациенту: "Сейчас соединю вас с администратором, который сможет посмотреть вашу историю"

**Настраивается при setup (индивидуально для каждого проекта):**
- Критерии квали-лида (что считать "горячим" лидом)
- Правила эскалации менеджеру (когда передавать)
- Вопросы для квалификации (BANT, SPIN, или кастомные)
- Рабочие часы менеджеров (когда можно эскалировать)
- ToV и стиль общения (из Tone of Voice Agent)

**Обновление базы знаний:**
- Ежедневный мониторинг сайта (3:00 AM)
- Автоматическое обновление цен/услуг в Obsidian
- Webhook при изменении (если CMS поддерживает)

## Блок 4: Результаты и метрики

**Q9: Что возвращает агент?**

A:

**Комментарий:** Что возвращает агент? Тут в зависимости от CRM, наверное, всю историю сообщений, естественно, должен возвращать. Историю сообщений и, возможно, какую-то квалификацию лида уже первоначально ставит в CRM. Давай подумаем здесь еще получше. Какие данные могут быть? Если пациент оставил свой номер телефона или что-то прочее, то, естественно, все это должно автоматически подтягиваться в CRM и передаваться на менеджера.

**Комментарий:** Там есть стандартный набор: UTM-метки, геолокации и прочая информация, которая может подтягиваться в CRM-ку. Всё, что может агент раздобыть, надо подтягивать. Ну, наверное, в какие-то заметки там или еще куда-то.

**В CRM (основное хранилище):**

**Обязательные поля:**
- `lead_id` — ID лида в CRM
- `status` — статус квалификации (cold/warm/hot/qualified)
- `conversation_history` — полная история диалога
- `contact_name` — имя (если пациент назвал)
- `contact_phone` — телефон (если оставил)
- `contact_email` — email (если оставил)
- `source_channel` — канал (telegram/instagram/vk/whatsapp/website)
- `first_message_time` — когда написал первый раз
- `response_time` — время реакции агента (секунды)

**Квалификация:**
- `need` — что беспокоит, какая услуга интересует
- `urgency` — когда нужна консультация (срочно/на неделе/не срочно)
- `budget_discussed` — обсуждался ли бюджет (true/false)
- `ready_to_book` — готов записаться (true/false)

**Дополнительные данные (всё, что удалось раздобыть):**
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` — UTM-метки
- `geo_location` — геолокация (если доступна)
- `device_type` — тип устройства (mobile/desktop)
- `previous_interactions` — предыдущие обращения (если есть)
- `interested_services` — интересующие услуги
- `interested_doctors` — интересующие врачи
- `unanswered_questions` — вопросы, на которые агент не смог ответить

**Метаданные:**
- `agent_version` — версия агента
- `conversation_duration` — длительность диалога (минуты)
- `messages_count` — количество сообщений в диалоге
- `escalated_to_manager` — передан менеджеру (true/false)
- `escalation_reason` — причина эскалации (если была)

**В Obsidian (резервное + аналитика):**
- Копия диалога для анализа
- Статистика по агенту (конверсия, время ответа)
- Неотвеченные вопросы (для улучшения базы знаний)

**Q10: Какие метрики качества?**

A:

**Комментарий:** Это и конверсия в QualiLid. Прям круто. То есть хорошие метрики. Вряд ли агент продаст, но если можно будет подцепить какие-то бизнес-метрики сюда, было бы круто. Вряд ли он продаст без менеджера. С другой стороны, может быть, стоит заложить такую механику.

**Производительность:**
- **Success rate:** > 95% (агент ответил без ошибок)
- **Response time:** < 30 секунд (среднее время первого ответа)
- **Conversation duration:** < 5 минут (среднее время до квалификации)

**Качественные метрики:**
- **Конверсия в квали-лид:** > 30% (из всех обращений)
- **Escalation rate:** < 20% (процент эскалаций менеджеру)
- **Patient satisfaction:** > 4.5/5 (оценка пациента после диалога, опционально)

**Бизнес-метрики (через CRM):**
- **Квали-лид → Запись:** > 50% (сколько квали-лидов записались на консультацию)
- **Квали-лид → Продажа:** > 20% (сколько квали-лидов стали клиентами)
- **Revenue per lead:** средний чек от лидов агента

**Специфичные метрики:**
- **152-ФЗ compliance:** 100% (все запросы медицинских данных эскалированы)
- **Knowledge base coverage:** > 90% (процент вопросов, на которые агент смог ответить)
- **Price accuracy:** 100% (актуальность цен в базе знаний)

## Блок 5: Особенности и edge cases

**Q11: Какие специфичные ошибки?**

A:

**Комментарий:** Технические сбои либо какое-то неадекватное поведение пациента, например, начинает там бузить, грузить. То есть нужен протокол, которым действуют при неадекватном поведении пациента.

**Технические ошибки:**

1. **API_UNAVAILABLE** — API канала недоступен (Telegram/Instagram/VK down)
   - Действие: Retry 3 раза (30 секунд интервал)
   - Если не помогло → логировать, уведомить администратора
   - Пациенту: "Извините, технические неполадки. Попробуйте через 5 минут или позвоните нам"

2. **CRM_CONNECTION_ERROR** — CRM не отвечает
   - Действие: Retry 3 раза (10 секунд интервал)
   - Если не помогло → сохранить диалог в Obsidian (резервное хранилище)
   - Синхронизировать с CRM позже (когда восстановится)
   - Продолжить диалог с пациентом (не прерывать)

3. **OPENAI_API_ERROR** — OpenAI API недоступен
   - Действие: Fallback на DeepSeek / Qwen (китайские модели)
   - Если и они недоступны → шаблонные ответы (FAQ)
   - Эскалация менеджеру, если вопрос сложный

4. **KNOWLEDGE_BASE_OUTDATED** — база знаний устарела (цены изменились на сайте)
   - Действие: Предупредить пациента "Уточню актуальную информацию"
   - Запустить внеплановое обновление базы знаний
   - Эскалация менеджеру для точного ответа

**Поведенческие ошибки:**

5. **INAPPROPRIATE_BEHAVIOR** — неадекватное поведение пациента (мат, угрозы, спам, троллинг)
   - **Протокол:**
     1. Первое нарушение: Вежливое предупреждение ("Пожалуйста, давайте общаться уважительно")
     2. Второе нарушение: Эскалация менеджеру + уведомление администратора
     3. Третье нарушение: Блокировка пользователя (добавление в чёрный список)
   - Логирование всех инцидентов в CRM + Obsidian
   - Критерии: мат, угрозы, оскорбления, спам (> 10 сообщений в минуту), троллинг

6. **MEDICAL_DATA_REQUEST** — пациент просит медицинские данные (152-ФЗ)
   - Действие: Немедленная эскалация менеджеру (без попыток ответить)
   - Сообщение: "Сейчас соединю вас с администратором, который сможет посмотреть вашу историю"
   - Логирование запроса (для аудита 152-ФЗ)

7. **COMPLEX_QUESTION** — вопрос слишком сложный (агент не знает ответа)
   - Действие: Честно признать "Не могу точно ответить, сейчас соединю с администратором"
   - Эскалация менеджеру
   - Логирование вопроса (для улучшения базы знаний)

**Q12: Что в backlog?**

A:

**Комментарий:** Можно расширить и сравнивать, например, с тем, что мы берем коммуникации в Brand Magister, вот эту всю историю. А Tone of Voice сравнивать проще, то есть можно давать какие-то выводы для остальных участников системы.

**Функции для будущего:**

1. **Интеграция с Brand Magister** — передача истории коммуникаций для анализа ToV
   - Сравнение реальных диалогов с эталонным ToV
   - Выводы и рекомендации для улучшения коммуникации
   - Обучение других агентов на успешных диалогах

2. **A/B тестирование ответов** — тестирование разных вариантов ответов
   - Какие формулировки лучше конвертируют в квали-лид
   - Оптимизация вопросов для квалификации
   - Автоматическое улучшение на основе результатов

3. **Аналитика тональности** — анализ эмоций пациента
   - Определение настроения (позитивное/нейтральное/негативное)
   - Адаптация стиля общения под настроение
   - Раннее выявление недовольных пациентов

4. **Продажа простых услуг без менеджера** — автоматическая продажа консультаций
   - Оплата онлайн (интеграция с платёжными системами)
   - Автоматическая запись в календарь
   - Отправка подтверждения и напоминаний

5. **Мультиязычность** — поддержка нескольких языков
   - Автоматическое определение языка пациента
   - Ответы на английском, армянском, узбекском (для Москвы)
   - Перевод через OpenAI API

6. **Проактивные сообщения** — агент пишет первым
   - Напоминания о записи (за день до консультации)
   - Опросы после визита (NPS, отзывы)
   - Специальные предложения (акции, скидки)

## Инсайты и решения

**Ключевые решения:**

1. **База знаний в Obsidian** — структурированная, обновляемая, изолированная для каждого проекта
2. **Мониторинг сайта через API** — WordPress REST API / Bitrix24 REST API (не Playwright)
3. **152-ФЗ compliance** — медицинские данные → немедленная эскалация
4. **Протокол неадекватного поведения** — предупреждение → эскалация → блокировка
5. **Setup под каждый проект** — квалификация, ToV, правила эскалации настраиваются индивидуально
6. **Deployment на сервере 24/7** — не локально, круглосуточная доступность
7. **Изоляция проектов** — каждый проект = отдельный агент с отдельной базой знаний
8. **Голосовое общение** — Assembly AI + OpenAI GPT-4o-mini + fallback на китайские модели
9. **Всё в CRM** — даже незначительные коммуникации сохраняются
10. **Предпродажная квалификация** — превращение холодного лида в квали-лид деликатно
