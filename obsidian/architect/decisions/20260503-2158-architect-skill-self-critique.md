# Strategic Decision: Update /architect skill with built-in self-critique

## Question
Задокументировал ли ты систему самоулучшения и будешь ли ей следовать при работе через /architect?

## Context
- Система самоулучшения полностью создана (Gatekeeper + Critic + Retrospective)
- Все правила задокументированы в коде
- НО: я (Claude Code) не могу автоматически следовать правилам между сессиями
- Нужна интеграция в /architect skill

## Decision
Обновить /architect skill со встроенной самокритикой (5 проверок качества).

## Rationale

### Проблема:
Я не имею постоянной памяти между сессиями и не могу автоматически применять правила Critic. Нужна интеграция в сам skill, чтобы правила применялись каждый раз.

### Решение:
Добавить в /architect skill обязательный этап самокритики ПЕРЕД показом решения пользователю.

### Почему это лучший подход:
1. **Автоматизация** - правила применяются каждый раз автоматически
2. **Качество** - каждое решение проходит 5 проверок
3. **Прозрачность** - пользователь видит результаты самокритики
4. **Простота** - не нужно вызывать отдельные компоненты

### Учёт прошлого опыта:
- Gatekeeper показал эффективность автоматических проверок
- Critic успешно выявляет проблемы в решениях
- Интеграция в workflow лучше чем отдельные компоненты

### План отката:
Если skill станет слишком строгим или медленным:
1. Можно отключить проверки через параметр
2. Можно ослабить пороги (например, требовать 1 альтернативу вместо 2-3)
3. Можно вернуться к старой версии skill (git revert)

## Confidence
92%

## Alternatives Considered

1. **Отдельный skill /architect-with-critic**
   - Pros: Не ломает существующий workflow
   - Cons: Сложнее использовать, нужно помнить два skill
   
2. **Ручная проверка пользователем**
   - Pros: Полный контроль
   - Cons: Требует времени, можно пропустить проблемы
   
3. **Обновить существующий /architect** ✅ ВЫБРАНО
   - Pros: Автоматически, просто, качественно
   - Cons: Может замедлить генерацию решений

## Risks

1. **Skill может стать слишком сложным**
   - Митигация: Чёткая структура, понятные правила
   - Вероятность: низкая
   
2. **Может замедлить генерацию решений**
   - Митигация: Проверки быстрые (< 10 секунд)
   - Вероятность: низкая
   
3. **Может быть слишком строгим**
   - Митигация: Настраиваемые пороги, можно ослабить
   - Вероятность: средняя
