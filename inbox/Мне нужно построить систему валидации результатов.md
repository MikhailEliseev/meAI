# Мне нужно построить систему валидации результатов AI-агентов для

конкурентного анализа сайтов. Конкретно: агент технического
SEO-аудита анализирует сайты конкурентов и возвращает результаты с
оценкой качества 0-100%.

ПРОБЛЕМА: Агент вернул 4 сайта с оценкой 100% (идеально) и 1 сайт
с 0% (провал). Это выглядит подозрительно — либо агент
поверхностно анализирует, либо не находит реальные проблемы.

КОНТЕКСТ СИСТЕМЫ:

- Агент анализирует: Core Web Vitals, мобильную версию, структуру
URL, техническое SEO, доступность
- Использует Playwright для рендеринга и анализа
- Должен анализировать 50+ страниц сайта (не только главную)
- Работает в медицинской нише (косметология, стоматология)

МОИ ВОПРОСЫ:

не поверхностным?

технического аудита?
- Какие красные флаги указывают на то, что агент работает
некачественно?

AI-агентов?
- Какие автоматические проверки можно добавить для валидации

- Как отличить "агент не нашёл проблем" от "агент плохо искал"?

3. ТЕХНИЧЕСКИЙ АУДИТ — ЧТО ПРОВЕРЯТЬ:

## Чеклист метрик качества технического аудита

### 1. Метрики покрытия (coverage)

Что собирать для каждого запуска аудита сайта:

- pages_crawled: уникальных URL, реально отрендеренных Playwright’ом (цель: ≥50, минимум ≥20 даже для очень маленьких сайтов).
- templates_covered: типы страниц (главная, услуги, список услуг, карточка услуги, блог‑листинг, статья, контакты/запись, FAQ, политика) — цель: ≥5–7 типов.
- depth_max: максимальная глубина от главной (цель: ≥3).
- cwv_pages_sampled: на скольких страницах считали Core Web Vitals / скорость (минимум 10–20).[^3][^4][^5]

Правило валидации:
если `pages_crawled < 20` или `templates_covered < 3` → помечаем аудит как `LOW_COVERAGE`, score обрезаем сверху (например, max 70) и шлём на human review.

***

### 2. Метрики глубины (depth)

Для каждой страницы:

- checks_per_page: количество проверок (CWV, mobile, SEO‑элементы, доступность, security). На реальном чеклисте их 30–50+ на сайт.[^6][^5][^7]
- issues_checked_but_ok: количество проверок, по которым пришёл “OK” (чтобы отличать “не нашли проблему” от “вообще не смотрели”).
- tools_used: какие внешние инструменты запускались (PageSpeed/Lighthouse, axe‑core и т.п.).[^8][^5]

Сводный критерий глубины по сайту:

- avg_checks_per_page ≥ 15–20.
- доля полей в отчёте, где `value = null / not collected`, < 10–15%.

Если `avg_checks_per_page < 10` или много `null` → агент явно “скользит по поверхности”, автоматический флаг `SHALLOW_AUDIT`.

***

### 3. Метрики “формы” результата (sanity / shape)

Для всего батча сайтов (например, 5 конкурентов):

- score_distribution: разброс оценок, стандартное отклонение. В реальности у конкурентов редко **4×100 и 1×0**, обычно есть широкий диапазон.[^9][^3]
- findings_count: кол-во найденных проблем (critical / major / minor) на сайт. На живых сайтах почти всегда есть несколько минорных проблем по скорости, доступности, микроразметке, и т.д.[^4][^5][^10][^8]
- time_spent: wall‑time или суммарное время рендеринга всех страниц (подозрительно, если на “большой” сайт ушло 5–10 секунд).

Примеры правил:

- если `score == 100` и `(critical_issues + major_issues + minor_issues) == 0` → флаг `SUSPICIOUS_PERFECT_SCORE`.
- если все сайты в батче получили значения в диапазоне [95;100] → флаг `LOW_VARIANCE_BATCH`.
- если `time_spent < min_expected_time(pages_crawled)` → флаг `TOO_FAST_TO_BE_TRUE`.

***

### 4. Метрики консистентности с внешними источниками

Сравниваем то, что видит агент, с внешними сервисами:

- CWV/скорость: PageSpeed Insights / Lighthouse (LCP, INP, CLS).[^5][^4][^8]
- mobile usability: Google Mobile Friendly / GSC Mobile Usability / Lighthouse mobile.[^3][^4][^5][^9]
- indexation/crawl errors: Google Search Console (если есть доступ).[^8][^9]
- accessibility score: axe‑core / Lighthouse accessibility vs ваши внутренние оценки.[^10][^11][^12]

Примеры правил:

- если агент ставит “скорость: отлично”/score > 90, а PageSpeed mobile показывает “красную зону” (LCP > 4s, INP > 500ms, CLS > 0.25) → флаг `EXTERNAL_MISMATCH_CWV`.[^4][^5]
- если агент пишет “доступность отличная”, а axe‑core/Lighthouse даёт < 80 баллов → флаг `EXTERNAL_MISMATCH_A11Y`.[^11][^12][^10]

***

### 5. Метрики качества самого агента

Поверх одного аудита нужны глобальные метрики качества агента:

- pass_rate на “golden set” (сайты с заранее размеченными проблемами и эталонными выводами). Это стандартная практика для AI‑агентов.[^13][^14][^1]
- agreement_rate с “LLM‑судьёй” (более сильная модель/другой агент, оценивающий корректность отчёта).[^2][^1][^13]
- regression_trend: график качества на golden‑датасете после каждого деплоя (чтобы ловить деградацию).[^14][^1]

## Архитектура системы валидации результатов

### 1. Слои (multi‑layer validation)

Рекомендованная трёхслойная схема:[^1][^2][^13]

1. Execution‑агент (Technical SEO Agent)
    - Скрапит и рендерит Playwright’ом.
    - Считает локальные метрики (CWV по Lighthouse, доступность по axe‑core, структура URL, мета‑теги и т.д.).[^5][^10][^3][^8]
2. QA‑валидатор (детерминированный + LLM‑валидатор)
    - Проверяет coverage, depth, sanity, консистентность с внешними API.
    - Опционально вызывает LLM‑as‑a‑judge, чтобы оценить качество отчёта.[^2][^13][^1]
3. Human‑оператор
    - Смотрит только на визарды с флагами (`SUSPICIOUS_PERFECT_SCORE`, `LOW_COVERAGE`, `EXTERNAL_MISMATCH_*` и т.п.).
    - Может помечать выводы как `correct/incorrect`, пополняя golden‑датасет.[^13][^14][^1]

***

### 2. Пример простого пайплайна (псевдокод)

```ts
type SiteAuditResult = {
  site: string;
  score: number;
  issues: Issue[];             // {severity: 'critical'|'major'|'minor', code: string}
  coverage: {
    pagesCrawled: number;
    templatesCovered: number;
    depthMax: number;
    cwvPagesSampled: number;
  };
  metrics: {
    avgChecksPerPage: number;
    cwvSummary: { lcp: number; inp: number; cls: number; };
    a11yScore: number;
    mobileOk: boolean;
  };
  rawEvidence: EvidenceRef[];  // ссылки на HTML снапшоты, HAR, JSON метрик
};

type QaVerdict = {
  status: 'OK' | 'SUSPECT' | 'REJECT';
  flags: string[];
};

async function runAuditWithValidation(domain: string): Promise<{audit: SiteAuditResult; qa: QaVerdict}> {
  const audit = await technicalSeoAgentAudit(domain); // ваш агент

  const qaFlags: string[] = [];

  // 1) Coverage
  if (audit.coverage.pagesCrawled < 20) qaFlags.push('LOW_COVERAGE');
  if (audit.coverage.templatesCovered < 3) qaFlags.push('LOW_TEMPLATE_DIVERSITY');

  // 2) Depth
  if (audit.metrics.avgChecksPerPage < 10) qaFlags.push('SHALLOW_AUDIT');

  // 3) Suspicious perfect score
  const totalIssues = audit.issues.length;
  if (audit.score === 100 && totalIssues === 0) qaFlags.push('SUSPICIOUS_PERFECT_SCORE');

  // 4) External cross-checks
  const psi = await fetchPageSpeedMobile(domain);   // LCP / INP / CLS из PageSpeed API
  if (audit.metrics.cwvSummary.lcp < 2.5 && psi.lcp > 4.0) {
    qaFlags.push('EXTERNAL_MISMATCH_CWV');
  }

  const a11y = await runAxeOnSamplePages(domain);
  if (audit.metrics.a11yScore > 90 && a11y.score < 80) {
    qaFlags.push('EXTERNAL_MISMATCH_A11Y');
  }

  // 5) LLM-as-a-judge (опционально)
  const judge = await llmJudgeAuditQuality(audit, psi, a11y);
  if (judge.rating < 0.7) qaFlags.push('LLM_JUDGE_LOW_SCORE');

  const status: QaVerdict['status'] =
    qaFlags.length === 0 ? 'OK'
    : qaFlags.includes('LOW_COVERAGE') || qaFlags.includes('SUSPICIOUS_PERFECT_SCORE') ? 'REJECT'
    : 'SUSPECT';

  return { audit, qa: { status, flags: qaFlags } };
}
```

Этот слой вы можете оформить как отдельный сервис/воркер, который подписан на очередь с результатами агента.

### 3. Как отличить “агент не нашёл проблем” от “агент плохо искал”

Внедрите **обязательные доказательства** и контр‑примеры:

1. Для каждого типа проверки требуйте:
    - список страниц, по которым она реально выполнялась;
    - числовые метрики (например, конкретные значения LCP/INP/CLS, размер HTML, количество 4xx/5xx и т.п.).[^4][^8][^5]
2. При каждом прогоне добавляйте **контрольные сайты**:
    - 1–2 “плохих” сайта с известными серьёзными проблемами;
    - 1 “хороший” сайт‑бенчмарк.
Агент должен стабильно выдавать им ожидаемые баллы (low / high). Это практикуется в тестировании AI‑агентов.[^14][^1][^13]
3. Сэмплируйте X% сайтов для **full external audit**:
    - прогон через Screaming Frog/Sitebulb, PageSpeed, Lighthouse, axe‑core;
    - сверка с отчётом агента;
    - расхождения отправляйте в retraining / prompt‑тюнинг.

Если агент заявил “идеально”, но **не смог предъявить данные** (например, нет списка проверенных страниц, нет реальных CWV‑значений), — это автоматически трактуется как “плохо искал”.

## Обязательные проверки технического SEO‑аудита

Ниже — минимальный продакшн‑чеклист (категории + несколько ключевых проверок), опирается на современные чеклисты тех. SEO.[^15][^7][^6][^9][^3][^8][^5][^4]

### 1. Crawlability и indexation

- HTTP‑коды: нет 5xx, минимально 4xx, корректные 3xx.
- robots.txt: существует, не блокирует критичные разделы.
- XML‑sitemap: есть, валидна, покрывает ключевые разделы.
- Canonical‑теги: корректны, нет самопротиворечий.


### 2. Архитектура и URL

- ЧПУ‑URL, без лишних параметров для основного контента.
- Глубина вложенности ключевых страниц ≤ 3 клика от главной.[^3][^4]
- Внутренняя перелинковка: нет “осиротевших” страниц, логичные хлебные крошки.


### 3. Core Web Vitals и скорость

- LCP < 2.5s, INP < 200ms, CLS < 0.1 (идеальная цель, особенно на мобильных).[^4]
- Размер HTML и critical‑ресурсов (CSS/JS) разумный, нет блокирующих огромных бандлов.
- Кэширование, сжатие (gzip/brotli), HTTP/2/3.


### 4. Мобильная версия

- Responsive дизайн, корректный viewport meta.[^8][^5][^3]
- Нет горизонтального скролла, кликабельные элементы не слишком мелкие.[^5][^4]
- Контент мобильной версии не хуже по объёму/качеству, чем десктоп.[^6][^9]


### 5. HTTPS и безопасность

- Весь сайт на HTTPS, нет mixed content.[^10][^11][^8]
- Корректные SSL‑сертификаты, современные протоколы.
- HSTS, базовые security‑заголовки (Content‑Security‑Policy, X‑Frame‑Options и т.п.).


### 6. Техническое on‑page SEO

- Один H1 на страницу, логичная иерархия H2–H3.
- Meta title и description присутствуют и уникальны (хотя бы на важных страницах).[^15][^6]
- Open Graph / Twitter Cards для шаринга.
- Структурированная разметка (Schema.org) для организаций, услуг, FAQ, отзывов и т.д.[^3][^5]


### 7. Доступность (особенно важна для медицины)

- Alt‑тексты для ключевых изображений.[^12][^11][^10]
- Корректная семантическая разметка (landmarks, headings).
- Контраст текста по WCAG 2.1 AA; навигация с клавиатуры; формы доступны для скринридеров.[^12]


### 8. Логи и ошибки

- Доля 4xx/5xx от общего числа URL.
- Частые redirect‑цепочки.
- Custom 404 страница.


### 9. Специфика медицины

- Страницы с формами записи / запросом персональных данных — только по HTTPS, без утечек в сторонние скрипты.[^11][^10][^12]
- Наличие политики конфиденциальности, согласий, cookie‑баннера.
- Отдельный чеклист доступности по WCAG 2.1 AA (обязателен для healthcare‑сайтов в США и ряде юрисдикций).[^10][^11][^12]

## Инструменты и API для кросс‑валидации

### 1. Скорость и Core Web Vitals

- Google PageSpeed Insights API (field + lab data по LCP, INP, CLS).[^5][^4]
- Lighthouse CLI/CI (как отдельный процесс поверх Playwright’а).[^8][^5]
- Chrome UX Report (если нужен реальный полевой CWV).


### 2. Мобильная пригодность

- Lighthouse в режиме mobile.
- Данные Google Search Console: Mobile Usability report (через API).[^9][^3][^4]


### 3. Краулер/структура

- Screaming Frog SEO Spider (CLI) — можно запускать как часть пайплайна.
- Sitebulb / custom crawler на базе Playwright + очереди URL.[^7][^6]


### 4. Доступность

- axe‑core (JS‑библиотека, легко интегрируется в Playwright).
- Lighthouse accessibility score.[^11][^12][^10]
- WAVE API для дополнительной проверки.


### 5. Безопасность и HTTPS

- SSL Labs API для проверки сертификатов и настроек.
- securityheaders.com API (Content‑Security‑Policy и др.).
- Собственные проверки на mixed content и HSTS.


### 6. Медицинская специфика

- Набор ручных/полуручных чеков на соответствие HIPAA/ADA/WCAG (тут без полностью автоматического API, но можно автоматизировать часть: HTTPS, наличие политик, анонимность логов и т.п.).[^12][^10][^11]


### 7. QA для AI‑агента

- LLM‑as‑a‑judge (тот же или более сильный LLM, но отдельный промпт и роль валидатора).[^1][^13][^14]
- Система golden‑датасетов + автоматические “evals” при каждом изменении агента.[^13][^14][^1]

## “Здоровые” и “подозрительные” метрики качества

### 1. Для самого сайта (как объекта аудита)

Примеры “здоровых” значений (идеалы, к которым вы можете нормировать score):

- CWV: LCP < 2.5s, INP < 200ms, CLS < 0.1 на большинстве страниц (или по данным field data).[^4]
- Lighthouse performance / accessibility / best‑practices ≥ 80–90, но при этом всё равно есть 1–5 минорных предупреждений.[^10][^8][^5]
- 4xx < 1–2% от общего числа известных URL, 5xx ≈ 0.
- Нет критичных проблем мобильной пригодности в GSC.
- Нет страниц без title / H1 среди основных шаблонов.

**Подозрительно “слишком хорошо”:**

- 0 найденных issues вообще.
- Все Lighthouse‑скоры 100/100/100/100 более чем на нескольких десятках страниц (на реальных меди‑сайтах такое почти не встречается).[^8][^5][^4]
- Все конкуренты имеют общий итоговый score > 95 при явной визуальной разнице качества.

***

### 2. Для агента и его оценок

Нормальные паттерны:

- Распределение score по конкурентам:
    - 1–2 лидера (80–95),
    - несколько средних (50–80),
    - 0–1 явный аутсайдер (<50).
- На golden‑датасете агент правильно классифицирует ≥90% кейсов (хороший/плохой сайт, присутствие ключевых проблем).[^14][^1][^13]
- Доля запусков, помеченных QA‑флагами, в пределах 5–20% (иначе либо валидатор слишком строгий, либо агент деградирует).

Подозрительные паттерны:

- Много 100%‑оценок и практически нет значений в диапазоне 40–80.
- Нулевая корреляция между оценкой агента и внешними метриками (PageSpeed, Lighthouse, accessibility).
- При добавлении в батч заведомо “битого” тестового сайта агент по‑прежнему ставит ему высокие оценки.

***

### 3. “Проблемы, которые почти всегда есть” (полезно для sanity‑чеков)

На большинстве реальных коммерческих сайтов (особенно медицинских) можно почти всегда найти хотя бы нечто из этого:[^11][^12][^5][^10][^4][^8]

- Небольшие проблемы Core Web Vitals на мобильных (LCP чуть > 2.5s или INP > 200ms).
- Пара изображений без alt.
- Несколько страниц с “избыточными” заголовками H1/H2 или странной иерархией.
- Непараметризованные redirect‑цепочки или старые URL.
- Мелкие accessibility‑issues по WCAG (контраст, фокус‑стили, label’ы у форм).
- Meta descriptions, отсутствующие на второстепенных страницах.

Поэтому **полное отсутствие даже minor‑issues** почти наверняка означает, что агент что‑то не видит или не проверяет.
