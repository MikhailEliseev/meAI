# Исследование multi-tenant архитектуры для Hermes Agent

**Дата:** 2026-06-07
**Контекст:** Проектирование PM-системы для работы с сотнями/тысячами клиентов в изолированных Telegram-чатах.

---

## Проблема

Один инстанс Hermes Agent должен работать в нескольких Telegram-группах (чатах), в каждой группе — свой проект одного клиента. Клиенты не должны видеть друг друга (отдельные группы, не супергруппа). Данные клиента должны быть доступны из любого его проекта, но не из проектов других клиентов.

## Исследованные источники

### 1. GitHub Issue #34352 — "Solving the Multi-Tenant Hermes Problem"
https://github.com/NousResearch/hermes-agent/issues/34352

**Суть:** Предлагается `context_id` — при получении сообщения из группы, на MemoryStore устанавливается `context_id = chat_id`. Память пишется в `memories/contexts/{context_id}/MEMORY.md`. Глобальная память остаётся читаемой для всех контекстов.

**Автор:** NimbleCoAI (35 коммитов, ~70 строк ядра)
**Статус:** Open, не смержено
**Цитата:** *"Every Hermes deployment beyond personal use hits the same wall: one agent = one tenant."*

### 2. Telegram Topics (супергруппы)
Hermes поддерживает супергруппы с Topics: каждый thread_id → изолированная сессия.
**Но:** память всё равно глобальна.
**Михаил отклонил:** клиенты не должны видеть друг друга.

### 3. Reddit: "How to run Hermes Agent across multiple projects"
Подход: Telegram Topics — каждый топик = отдельный проект.
**Проблема:** глобальная память, нет изоляции данных.

### 4. Hermes Profiles
`hermes profile` — изолированные конфиги, скиллы, память. Теоретически можно сделать профиль на каждого клиента, но:
- Нет динамического переключения по chat_id
- Нужен gateway hook для роутинга
- Тяжеловесно для 1000+ клиентов

### 5. YouTube: "8 Tiers of Hermes Agent Project Isolation"
Обзор уровней изоляции: от простой конвенции до полного multi-tenant.

## Архитектурное решение

Выбрана **гибридная архитектура** без модификации ядра Hermes:

```
Уровень 1 — Telegram (отдельные группы)
  Каждый клиент = своя группа. chat_id — идентификатор.

Уровень 2 — Project Registry (JSON)
  chat_id → client_slug + project_slug. Flock-блокировка.

Уровень 3 — Per-project файлы
  /root/projects/{client}/{project}/ — context, data, files.

Уровень 4 — Second Brain (читается)
  /root/.knowledge/ — глобальный, read-only, git-версионирован.

Уровень 5 — Memory (Hermes встроенная)
  Только meta-инструкции (правила работы, инструменты).
  Не хранит данные клиентов.
```

## Почему не fork ядра

1. GitHub PR #34352 не смержен, может измениться
2. Fork требует поддержки при каждом обновлении Hermes
3. Файловая изоляция (уровень 3) — достаточна для MVP
4. Memory isolation можно добавить позже, когда PR примут

## Вывод

Система масштабируется на тысячи клиентов:
- Реестр: ~1KB на проект, 1000 проектов = 1MB
- Second Brain: ~10KB на клинику, 1000 клиник = 10MB
- Проекты: ~1-2MB на проект (скрапы, медиа, отчёты)
- Сессии: SQLite (state.db), миллионы записей
