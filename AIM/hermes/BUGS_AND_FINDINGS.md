## 🔴 CRITICAL

### C1: run_background_pipeline выполняется синхронно, а не fire-and-forget

**Ожидание (из spec):** "НЕ жди завершения пайплайна. run_background_pipeline — fire-and-forget. Клиент уже ушёл."

**Реальность:** Модель вызывает `run_background_pipeline` и ЖДЁТ его завершения синхронно. Pipeline запускает 12+ инструментов (включая повторный prescan на 500s), имеет таймаут 3600s. Клиент висит бесконечно.

**Причина:** `run_background_pipeline` — обычный синхронный tool. Модель не знает, что он fire-and-forget. После вызова она ждёт результат.

**Варианты исправления:**
1. Сделать инструмент асинхронным — он возвращает `{"status": "started", "session_hash": "..."}` мгновенно, а работа продолжается в фоне (ThreadPoolExecutor или asyncio.create_task)
2. Убрать `run_background_pipeline` из инструментов модели — вызывать его автоматически на стороне сервера после `collect_contact`

**Влияние:** Клиент не получает ответ после сбора контакта. Сессия обрывается по таймауту.

---

### C2: collect_contact → AIM API 500 ошибка

**Лог:**
```
ERROR app.tools.collect_contact: AIM API returned error for contact collection:
Server error '500 Internal Server Error' for url 'http://app:8000/api/leads'
```

**Причина:** Endpoint `POST /api/leads` на aim-app падает с 500. Нужно смотреть логи aim-app.

**Влияние:** Контакт не сохраняется. Лид не создаётся. Фаза перехода сломана полностью.

---

### C3: Модель систематически промахивается с параметрами на первом вызове

**Паттерн (воспроизводится в 100% тестов):**

| Инструмент | Ошибка первого вызова | Второй вызов |
|-----------|----------------------|-------------|
| `quick_overview` | `"url is required"` (0.00s) | Успешно |
| `collect_contact` | `"Either contact_type or website is required"` (0.00s) | Успешно |
| `run_background_pipeline` | `"session_hash is required"` (0.00s) | Успешно |

**Причина:** Модель (Opus 4.7) не всегда правильно заполняет параметры с первого раза. Возможно, описания инструментов в `tool_spec` недостаточно точны.

**Влияние:** +1 лишний API-вызов на КАЖДЫЙ инструмент. При цене Opus 4.7 это ~$0.01-0.03 за каждый промах. На пресейл: +3 вызова = +$0.03-0.09 лишних расходов.

**Исправление:** Уточнить `tool_spec` для всех инструментов: жёсткие примеры параметров, обязательные поля пометить жирным.

## 🟠 HIGH

### H1: Модель Opus 4.7 вместо Sonnet 4.6

**Сервер:** `LLM_MODEL=anthropic/claude-opus-4-7`
**Spec:** "Ожидаемое поведение Claude Sonnet 4.6"

**Сравнение стоимости (на пресейл):**
- Opus 4.7: ~$0.30-0.50 за вызов (5 API-вызовов, длинный контекст)
- Sonnet 4.6: ~$0.08-0.15 за вызов
- **Opus в 3-4x дороже**

**Дополнительно:** Opus думает медленнее. После prescan (535s) модели нужно ещё ~30-60s на генерацию ответа. Sonnet справился бы быстрее.

**Исправление:** `ssh aim "docker exec aim-hermes sed -i 's/LLM_MODEL=anthropic\\/claude-opus-4-7/LLM_MODEL=anthropic\\/claude-sonnet-4-6/' /opt/hermes/.env && docker restart aim-hermes"`

---

### H2: prescan находит неверную компанию по ИНН

**Данные prescan для nachalo-clinica.ru (Ростов-на-Дону, семейная клиника):**
> "диагностический центр в Санкт-Петербург, оборот 24.8 млн ₽, прибыль 82 тыс ₽"

**Проблема:** Название компании не совпадает. Город не совпадает. Тип организации не совпадает (диагностический центр vs семейная клиника).

**Вероятная причина:** Поиск компании по названию "Начало" находит не ту организацию. Нужно проверять по ИНН с сайта клиники.

**ИНН из ответа модели:** 6164142132 — нужно вручную проверить, та ли это компания.

**Влияние:** Финансовые данные в prescan могут быть от другой компании. Модель их использует для генерации ответа клиенту → дезинформация.

---

### H3: session_id теряется при таймауте

**Лог:**
```
ERROR app.agent_wrapper: run_agent asyncio timeout after 610s (no response salvaged): session=None
```

**При этом через 6 секунд:**
```
WARNING app.agent_wrapper: Agent finished just after timeout (600s): session=20260617_105513_a08162 — using real response
```

**Проблема:** Клиент уже получил `{"reply":"Извини, я задумался...", "session_id":null}` — а реальный ответ пришёл через 6 секунд после таймаута и был выброшен.

**Исправление:** В salvage-логике агента проверять, был ли ответ модели получен через несколько секунд после таймаута. Если да — вернуть его вместо заглушки.

## 🟡 MEDIUM

### M1: prescan занимает 500-535s (ожидание: 60-90s)

**По spec:** "run_prescan — ~60-90 секунд"
**Реальность:** 503s, 535s в двух тестах

**Причина:** prescan делает реальные HTTP-запросы к внешним API (nalog.ru, Яндекс.Карты, SEO-проверки). 3 стадии выполняются последовательно.

**Влияние:**
- Общее время пресейла: 22s (quick_overview) + 535s (prescan) + 30s (модель) = ~587s
- Таймаут Hermes должен быть > 600s
- Клиент ждёт 10 минут вместо 1.5

**Исправление:** Оптимизировать prescan — параллелить стадии где возможно, кэшировать результаты.

---

### M2: prescan Stage 2 слишком сжатый

**Stage 2 лог:**
> "SEO 60/100, соцсетей 2"

**Что отсутствует:**
- Нет анализа контента
- Нет технического стека
- Нет данных о скорости загрузки (хотя поле `web_speed` есть)
- Нет деталей по соцсетям (какие платформы, активность)

**Влияние:** Модель не может дать качественный разбор Stage 2. Ответ получается поверхностным.

---

### M3: prescan дублируется в background_pipeline

**Лог:**
```
background_pipeline: 🔬 Фаза 2 — глубокий анализ: запускаю 12 инструментов разведки…
full-scout: 🚀 Полный скаут: Клиника "Начало"
full-scout: Запуск: Prescan (Stage 1-3)…
prescan: 🎭 Запускаю 5 агентов разведки…
```

Prescan уже был сделан в Фазе 1 (за 535s). Background pipeline запускает его ПОВТОРНО.

**Влияние:** +500s лишнего времени в фоновом пайплайне. Данные уже есть в сессии.

**Исправление:** Передавать результаты prescan из Фазы 1 в background_pipeline. Или проверять кэш перед запуском.

## 🟢 LOW

### L1: quick_overview 16-22s вместо 5-10s

**По spec:** "quick_overview — ~5-10 секунд"
**Реальность:** 10.25s (nazub), 22.71s (nachalo-clinica)

**Причина:** Perplexity sonar-pro делает реальный поиск. Для сложных сайтов с большим количеством контента — дольше.

---

### L2: Нет параллельного выполнения инструментов

**Spec говорит:** "Claude вызывает quick_overview И run_prescan в одном tool_calls блоке (параллельно)"

**Реальность:** Модель возвращает оба tool_call в одном ответе, но Hermes выполняет их ПОСЛЕДОВАТЕЛЬНО (сначала quick_overview, потом prescan).

**Влияние:** Общее время = 22s + 535s = 557s. Если бы выполнялись параллельно: max(22s, 535s) = 535s. Экономия всего 22s — не критично при текущем prescan в 535s.

**Исправление:** `asyncio.gather()` для параллельных tool_calls в Hermes. Но сначала нужно ускорить prescan.

---

### L3: quick_overview возвращает 5562-6043 chars

При моделях с дорогим контекстом (Opus 4.7) каждый символ из quick_overview увеличивает стоимость генерации ответа. 6000 символов × $15/M output = ~$0.09 только на обработку результата quick_overview.

**Исправление:** Уменьшить размер `overview_text` до 1500-2000 символов (как в spec: "2-3 абзаца").

## Что работает хорошо

1. **Phase 1 параллельный вызов:** Модель действительно возвращает оба инструмента в одном `tool_calls` блоке
2. **quick_overview качество:** Perplexity даёт релевантные данные по клинике (6 секций)
3. **prescan 3 стадии:** Работают, возвращают структурированные данные
4. **session_id сохраняется:** При успешном завершении (без таймаута) сессия трекается
5. **Нарратив модели:** Opus 4.7 генерирует живой, убедительный текст с правильным тоном
6. **Переход к сбору контакта:** Модель естественно предлагает глубокий анализ и просит контакты
7. **Кэш OpenRouter:** 97-98% cache hit rate — модель переиспользует системный промпт
