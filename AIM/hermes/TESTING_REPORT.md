### 🔴 БАГ #2: run_prescan падает первые 2 раза (300s timeout × 2)

Первые два вызова `POST /api/presale/prescan-staged` → aim-app упали с таймаутом 300 секунд. Третий вызов сработал (245s).

**В логах aim-app НЕТ записей о первых двух вызовах** — значит, httpx на стороне Hermes не может достучаться до app:8000. Третий вызов проходит нормально.

**Причина (гипотеза):** DNS-резолв `app` → Docker IP не срабатывает с первого раза. Или connection pool в httpx.AsyncClient исчерпан.

**Влияние:**
- 600 секунд (10 минут!) потрачено на безуспешные попытки
- Модель зациклилась: fail → retry → fail → retry → успех
- Клиент получил таймаут вместо результатов

### 🔴 БАГ #9: quick_overview падает с Perplexity APITimeoutError (46.55s)

Perplexity API ответил через 46.55 секунд таймаутом. quick_overview вернул degraded-заглушку.

**Причина:** Perplexity API нестабилен. Таймаут в коде — 15s, но httpx ждал 46s.

### 🔴 БАГ #10: prescan-staged определяет НЕВЕРНЫЙ город!

### 🔴 БАГ #11: Модель входит в бесконечный цикл ретраев

Несмотря на `[Tool loop warning: repeated_exact_failure_warning; count=2]`, модель продолжает вызывать упавший инструмент. 3 вызова prescan + 2 вызова quick_overview = 5 tool calls вместо 2.

**Причина:** max_iterations=25 — слишком много. Нет жёсткого ограничения на повторные вызовы одного инструмента.

Результат третьего prescan пришёл через 245 секунд после начала третьей попытки, но общий asyncio timeout (910s) уже убил запрос. Клиент увидел: «Извини, я задумался и не успел ответить. Дай мне ещё секунду — повтори, пожалуйста.»

Хотя реальные данные УЖЕ были собраны.

### 🔴 БАГ #14: Ответ модели теряется при asyncio timeout

Модель завершила разговор через 961s и сгенерировала ответ 2755 символов:
```
Turn ended: reason=text_response api_calls=5/25 tool_turns=4 response_len=2755
Agent finished just after timeout (900s) — using real response
```

Но клиент УЖЕ получил таймаут-сообщение. Ответ сохранён в кэш агента, но НЕ доставлен клиенту.

**Причина:** asyncio.wait_for убивает HTTP-ответ ровно на 910s, даже если модель завершает работу через секунду после таймаута.

### 🔴 БАГ #15: Nginx proxy_read_timeout (600s) < Hermes asyncio timeout (910s)

Nginx для `/api/chat` имеет `proxy_read_timeout 600s`. Hermes имеет `_AGENT_TIMEOUT=900s` + 10s grace = `910s`. Nginx оборвёт соединение на 600 секундах раньше, чем Hermes! Клиент получит 504 Gateway Timeout вместо ответа.

Для `/api/` (другие endpoints): `proxy_read_timeout 300s`.

**Исправление:** Согласовать таймауты. Nginx должен быть выше, чем Hermes (или Hermes ниже, чем nginx).

**Это архитектурная проблема.** Схема «вызови оба параллельно» неработоспособна на DeepSeek.

**Причина:** Модель ждёт результатов ВСЕХ tool calls перед ответом. Промпт говорит «покажи СРАЗУ», но модель физически не может прервать tool_calls блок.

### 🟡 БАГ #6: Каждый пресейл-запрос стоит ~$2-4 на Claude Opus 4.7


### 🟡 БАГ #7: max_iterations=25 для PRESALE — слишком много

Каждая итерация = один Claude Opus 4.7 вызов. 25 итераций = потенциально $15+ на один запрос. Для PRESALE нужно max_iterations=5.

### 🟡 БАГ #8: Нет retry с backoff в tool handler

При падении `run_prescan` — нет автоматического retry. Модель сама решает повторить, тратя лишние токены. Retry должен быть в коде handler'а, а не в модели.

## Анализ: почему архитектура не работает с DeepSeek

Текущая архитектура Фазы 1 спроектирована под возможности Claude:

```
Claude может:                          DeepSeek НЕ может:
├─ Параллельные tool calls             ├─ Только последовательные вызовы
├─ Показывать текст между вызовами     ├─ Один ответ после всех вызовов
├─ Стриминг во время ожидания          ├─ Полная тишина пока ждёт
└─ Сам выбирает стратегию              └─ Нужна явная пошаговая инструкция
```

**DeepSeek V4 Pro при вызове двух инструментов:**
1. Вызывает tool #1 → ждёт результат
2. Вызывает tool #2 → ждёт результат
3. Пишет ответ (ОДНО сообщение со всеми данными)

**Невозможно реализовать на DeepSeek:**
- ❌ «Покажи quick_overview СРАЗУ, не жди prescan»
- ❌ «Рассказывай по стадиям: сначала финансы, потом SEO, потом рынок»
- ❌ «Вызови оба инструмента в одном tool_calls блоке»

## Предлагаемое решение: универсальная архитектура

### Фаза 1 разбивается на 2 отдельных раунда

```
Раунд 1: quick_overview (~5-10s)
  ├─ Модель вызывает ТОЛЬКО quick_overview
  ├─ Получает результат → сразу показывает клиенту
  └─ WOW-эффект: «Ого, откуда он это знает за 5 секунд?!»

Раунд 2: run_prescan (~60-90s)
  ├─ Модель вызывает run_prescan (один инструмент)
  ├─ Получает 3 стадии в одном ответе
  └─ Рассказывает клиенту 3 сообщениями
```

**Преимущества:**
- Работает на ЛЮБОЙ модели (Claude, DeepSeek, GPT, Gemini)
- quick_overview всегда показывается первым (WOW-эффект)
- Меньше токенов: 2 вызова вместо 4-6
- Проще дебажить: нет параллельных гонок

**Недостатки:**
- Общее время: 5s + 90s = 95s (вместо 90s при параллельном)
- На 5 секунд дольше — некритично

### Реализация

Вместо «вызови оба параллельно» → «сначала вызови quick_overview, покажи клиенту, потом вызови run_prescan».

Это изменение только в промпте `_presale_prompt()`. Код инструментов не меняется.

### 🔴 БАГ #17: hermes-agent — модель не передаёт параметры без hermes-debug

При `enabled_toolsets = ["aim-operations"]` (только один toolset), модель вызывает ВСЕ инструменты без параметров:
- `quick_overview` → `{"error": "url is required"}`
- `run_prescan` → `{"error": "url is required"}`  
- `orchestrate` → `{"error": "operation is required"}`

При `enabled_toolsets = ["aim-operations", "hermes-debug"]` — всё работает нормально.

**Причина:** Баг в `hermes-agent` фреймворке. Tool definitions некорректно передаются в OmniRoute/LLM когда зарегистрирован только один toolset.

**Workaround:** Всегда включать `hermes-debug` даже для PRESALE. Запретить `api_debug` и `orchestrate` в промпте.
